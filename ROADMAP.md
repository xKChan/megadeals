# Mega Deals Canada — Roadmap & Recommendations

_Last updated 2026-08-21_

## Where things stand

`scripts/syncDeals.js` is a working pipeline: it discovers candidate deals via Keepa's Deals API (recent Amazon.ca price drops, no more hardcoded ASIN list), enriches each one with Keepa's price history and an all-time-low flag, cross-checks price/availability directly against Amazon via the Creators API, generates a Link TW affiliate link, and upserts into the Supabase `deals` table. The React/Vite frontend reads live rows from Supabase and renders them. All of this is running locally against real data.

## Done so far

**Amazon Creators API price verification (built 2026-08-20).** Every deal is confirmed directly against Amazon before it's published — Keepa updates on a delay, so this closes the window where a "deal" looks real in Keepa's data but has already expired or gone out of stock on Amazon. If Amazon has no listing or reports out-of-stock, the deal is skipped. When both sources have a price, Amazon's live price wins for what's actually displayed.

Worth knowing: the old Product Advertising API (PA-API 5.0) was fully retired May 15, 2026 — the Creators API is its mandatory replacement (OAuth 2.0, new endpoint). Access requires staying enrolled in Amazon Associates with at least 10 qualifying sales in the trailing 30 days — worth keeping an eye on, since losing that threshold cuts off this verification step. (Sources: [PA-API deprecation notice](https://affiliate-program.amazon.com/creatorsapi/docs/en-us/paapiv5-deprecation), [Creators API introduction](https://affiliate-program.amazon.com/creatorsapi/docs/en-us/introduction))

**Discovery at scale via Keepa's Deals API (built 2026-08-20).** `discoverDealAsins()` asks Keepa directly for recent Amazon.ca price drops (`MIN_DEAL_DISCOUNT_PERCENT`, default 30%+) instead of you tracking ASINs by hand — this is confirmed against Keepa's own documentation, so it's on solid ground. `DEAL_DISCOVERY_LIMIT` (default 20) caps how many candidates get run through the full verification pipeline per sync — each one costs a Keepa product lookup + a Creators API call + a LinkTwin call, so this is a real cost knob, not just a display cap.

**Second discovery mode: Keepa Product Finder (built 2026-08-21, experimental).** Based on a suggestion you brought from another AI, `discoverDealAsinsViaProductFinder()` queries Keepa's broader `/query` endpoint (category + sales rank + 90-day price trend + rating + review count), as an alternative to the Deals API's day-over-day price-drop feed. Switch between the two with `DISCOVERY_MODE=deals` (default) or `DISCOVERY_MODE=finder` in `.env.local` — one line, no code changes, and both functions stay in the script either way, so trying "finder" never risks losing the "deals" path. A git checkpoint commit was also made the same day as a second safety net. Heads up: most of the field names in the original suggestion didn't match Keepa's real API (verified against their docs before writing any code) — see `keepa_product_finder.md` in project memory for exactly what changed and why. Category scoping was also corrected the same day: the original 4 "include" category IDs (Electronics, Kitchen & Dining, Tools, Smart Home) turned out to be wrong for Amazon.ca — only one was a valid category at all, and it was actually Sports & Outdoors, which is why early finder-mode runs returned nothing but adidas gear. Fixed by switching to an EXCLUDE list (`categories_exclude`, `PRODUCT_FINDER_EXCLUDED_CATEGORY_IDS` in `.env.local`) built from a real, live Amazon.ca category lookup you ran — it excludes digital/media categories only (Alexa Skills, Amazon Appstore, Audible Books & Originals, Books, Kindle Store, Movies & TV, Music, Prime Video, Software) and allows everything else, rather than guessing at an include list.

**Variant de-duplication (built 2026-08-21).** Amazon color/size variants of one physical product are separate ASINs — the same soccer ball in size 3, 4, and 5 is three different ASINs, each of which can independently clear the discount filter, which is why near-identical cards were showing up for what's really one item. `dedupeAsinsByVariantFamily()` now runs right after discovery: it groups candidate ASINs by Keepa's `parentAsin` field (confirmed against Keepa's own `api_backend` source — the real "these are variants of the same product" signal) and keeps only the cheapest variant per group, before the costlier Creators API/LinkTwin calls run on the survivors. This is a discovery-time fix, entirely backend — duplicate rows already published from earlier runs stay in Supabase until re-synced or manually cleaned up. A fuller "one card, pick your size" experience (all live variants shown together with a size/color picker) is a separate, bigger feature — see "Still open" below.

**Raw discovery pool widened (fixed 2026-08-21).** After the parent-ASIN and variant-dedup fixes shipped, the first live GitHub Actions run only synced 2 new deals — not a bug, but a side effect of the fix working correctly: 17 of the 20 raw candidates Keepa returned turned out to be parent ASINs (one had 727 variations), leaving almost nothing after filtering. The old code sliced to `DEAL_DISCOVERY_LIMIT` (20) *before* filtering, so a parent-heavy raw feed could starve a run. Fixed with a new `DEAL_DISCOVERY_RAW_POOL` (default `DEAL_DISCOVERY_LIMIT * 4` = 80) — both discovery functions now pull a wider raw pool, `dedupeAsinsByVariantFamily()` filters it, and *then* the result is sliced back down to `DEAL_DISCOVERY_LIMIT` before the costly Creators API/LinkTwin stage runs. Trade-off: dedup now fetches more raw Keepa `/product` calls per run to check `isParentAsin`, so this is a real token-cost increase — watch the Actions log, and dial `DEAL_DISCOVERY_RAW_POOL` back down (env var) if Keepa starts rejecting requests.

**Cleaning up stale duplicate rows from before the variant-dedup fix.** The dedup/parent-ASIN fixes are discovery-time only — they don't touch rows already sitting in Supabase from before 2026-08-21. If you still see duplicate cards for the same product, that's old data, not the fix failing (check `created_at`/"Added X ago" on the card — if it predates the fix, that's the tell). Quickest cleanup: open the Supabase Table Editor, filter `deals` by title, sort by `deal_price`, and delete or set `is_active = false` on every row except the cheapest one per product. There's still no automated EXPIRE sweep to catch this going forward (see the sanity-guardrails note below) — worth building once compliance is done.

**EXPIRE sweep (built 2026-08-21).** A published deal used to stay `is_active: true` forever — discovery only ever looks at new/recently-dropped candidates, so a deal that quietly went out of stock or crept back up in price had no path back through the pipeline to get caught. Every sync run now ends with two passes: `refreshStaleActiveDeals()` pulls the `EXPIRE_REVERIFY_BATCH_SIZE` (default 10) stalest currently-active rows (oldest `last_verified_at` first) and re-runs them through the exact same verification pipeline as a new candidate — still discounted, still in stock, still passes every gate? It's re-upserted with a fresh `last_verified_at`; if it fails for any reason, it's deactivated immediately. `expireStaleDeals()` is a cheap safety-net pass after that (one Supabase update, no API calls) that deactivates anything not touched — by discovery or the refresh pass — within `EXPIRE_STALE_HOURS` (default 48), catching edge cases like an ASIN Keepa has delisted entirely. Cost note: the refresh pass spends real API budget per run (Keepa + Creators API + a new LinkTwin shortlink each time), on top of the raw-pool widening above — worth watching total run time/token usage in the Actions log. Tune `EXPIRE_REVERIFY_BATCH_SIZE` and `EXPIRE_STALE_HOURS` together: if the active-deal count grows faster than the batch size can cycle through within the stale-hours window, good deals could get expired just for still being in the queue — widen one or both if that starts happening. **Doesn't immediately fix today's known duplicate rows** — the Supabase migration that added `last_verified_at` backfilled every existing row (including the stale duplicates) to "now," so they won't hit the stale-hours cutoff for a while; they'll only get caught once one variant fails re-verification on its own, or once EXPIRE_STALE_HOURS genuinely elapses. For an immediate fix, the manual Table Editor cleanup noted above still applies.

**Affiliate link landing on the wrong page — fixed (2026-08-21).** Clicking "View Deal" was sometimes reaching Amazon but landing on a "choose your options" family page (price shown as a range, no size preselected) instead of the exact variant on the card. Traced by comparing a real LinkTwin shortlink against its actual redirect target: LinkTwin turned out to be an innocent pass-through (it redirected to exactly the same `amazon.ca/dp/{ASIN}?tag=...` URL our script built), which meant the ASIN itself was the problem — it was a **parent/family ASIN**, not a specific buyable child variant. Keepa's discovery occasionally surfaces a parent ASIN as a "deal" (Keepa tracks parents as trackable products in their own right, with a `variations` array — confirmed against Keepa's `api_backend` source), and a parent ASIN has no single price and no buyable `/dp/` page, so its affiliate link can never preselect a variant. Fixed with a new `isParentAsin()` guard, checked twice (once during variant dedup, once again independently in `buildDealPayload()`, matching this script's existing defense-in-depth pattern) — any ASIN Keepa marks as a parent is now excluded before it can ever be published. **Worth double-checking:** the redirect observed used `tag=84848-20` — confirm that matches your real `AMAZON_AFFILIATE_TAG` in `.env.local`; if it doesn't, clicks aren't earning you commission regardless of which page they land on.

## Current pipeline shape

```
1. DISCOVER  Keepa Deals API -> candidate ASINs (>= MIN_DEAL_DISCOUNT_PERCENT off)
2. DEDUP     group by Keepa parentAsin, keep the cheapest variant per group
3. ENRICH    Keepa product+stats -> price history, ATL flag, promo signals
4. VERIFY    Amazon Creators API GetItems(asin) -> live price + in-stock
5. RECONCILE live Amazon price wins for what's displayed; Keepa's is a
             fallback only if the Creators API price can't be parsed;
             no listing / out-of-stock -> skip, don't publish
6. PUBLISH   upsert to Supabase `deals`
7. EXPIRE    re-verify stalest active rows; deactivate anything that fails
             or goes untouched past EXPIRE_STALE_HOURS
```

## Still open, roughly in priority order

**Variant grouping UI — "one card, pick your size" (requested 2026-08-21, not built).** The backend dedup above stops duplicate cards from being published, but it only shows the cheapest variant. A fuller version — one card showing the product once with all its live on-sale sizes/colors as an in-card picker (matches a mockup you sketched) — needs a small backend contract change (publish a `parent_asin`/group key per deal row, or a variants array) plus new frontend rendering (group rows by that key client-side, render size/color chips inside one card, update the price/link when a chip is picked). Backend piece would live in this chat; frontend piece is separate work for whichever chat owns `DealCard.jsx`.

**Compliance — backend done (2026-08-21), frontend still needed.** The Amazon Associates Operating Agreement requires displayed prices to be accurate or clearly disclaimed. `buildDealPayload()` now sets `last_verified_at` (a fresh ISO timestamp) on every successful sync — this is the actual moment the Creators API cross-check confirmed the price against Amazon, re-set on every re-sync of an existing row, not just the first publish. **This requires a one-time Supabase migration** (run in the Supabase SQL Editor):

```sql
ALTER TABLE public.deals
  ADD COLUMN IF NOT EXISTS last_verified_at timestamptz NOT NULL DEFAULT now();
```

Without this column, every upsert will start failing (PostgREST rejects unknown columns) — run the migration before the next scheduled sync. Note: existing rows get backfilled to "now" at migration time as a placeholder: it's not literally when they were verified, but every row that's still actively discovered gets a real value within the next sync cycle (hourly), so this self-corrects fast.

**Frontend contract for whichever chat owns `DealCard.jsx`:** a `last_verified_at` column (ISO timestamp string) is now present on every row in the `deals` table. Render it as a "Price verified X ago" badge (same relative-time formatting already used for `created_at`'s "Added X ago" — `formatRelativeTime`/`formatAddedAt` in `App.jsx`/`DealCard.jsx` can be reused directly), distinct from the existing "Added" timestamp since they now mean different things: `created_at` = first published, `last_verified_at` = most recent confirmed-accurate check. This badge is the actual compliance requirement — don't skip it once the column exists.

**Orchestration/scheduling — done (2026-08-21).** `syncDeals.js` now runs automatically via `.github/workflows/sync-deals.yml` — an hourly GitHub Actions cron (`0 * * * *`, plus a manual "Run workflow" button), pushed to `github.com/xKChan/megadeals` with all 9 required secrets added in GitHub's Settings UI. First scheduled run completed successfully. Worth keeping an eye on: hourly means 24 runs/day, each burning Keepa tokens and Creators API calls — if the Actions log ever shows Keepa rejecting requests or the Creators API rate-limiting, drop the `cron:` line to every 3-6 hours (no other change needed). GitHub also auto-disables a scheduled workflow after 60 days with zero commits to the repo — any future push resets that clock, so it's a non-issue as long as the project keeps moving.

**Sanity guardrails — discount floor done, glitch-pricing ceiling still open.** Fixed 2026-08-20: cheap/generic ASINs (a $1.20 pipe coupling, a $2.99 Ethernet cable) were clearing Keepa's raw discount-% discovery filter but had no tracked MSRP, so the site was showing them with a fake "0% off" badge (list price silently defaulted to the deal price). `buildDealPayload()` now derives a real reference price (tracked MSRP, or the highest price actually seen in the last 30 days) and independently re-verifies the discount against `MIN_DEAL_DISCOUNT_PERCENT` before publishing — anything that can't clear the bar with real data gets skipped, not published. Still open: the *other* direction — Amazon "glitch pricing" (a $5 laptop typo, essentially) happens and gets corrected within minutes; a ceiling check (e.g. flag anything showing more than ~85–90% off for a human glance instead of auto-publishing) is cheap insurance on top of the Creators API cross-check. Also: the two bad rows published before that fix (LaSalle Bristol ABS coupling, Monoprice Ethernet cable) are sitting in Supabase with `is_active: true` — the EXPIRE sweep (see above) will eventually catch these once `EXPIRE_STALE_HOURS` elapses without them being re-verified, but for an immediate fix, deactivate them manually in the Table Editor.

**Category/brand narrowing — done (2026-08-20/21).** Discovery now filters to a brand allowlist (`DEAL_BRAND_ALLOWLIST` in `.env.local`, seeded with ~35 well-known consumer brands), a minimum product rating (`MIN_DEAL_RATING_STARS`, default 3.5), excludes books and DVDs, and requires a live Fulfilled-by-Amazon New offer — see `scripts/syncDeals.js`'s top comment and `getExcludedCategoryLabel()`/`hasLiveFbaNewOffer()` for how. Worth knowing: Amazon's Creators API has no fulfillment-channel field at all in its offersV2 response, so the FBA check reads Keepa's own per-offer data instead — Keepa is now the source of truth for that, not Amazon's API.

**Rate limits & token budgets.** Keepa charges tokens per request (the deals discovery call is 5 tokens per up to 150 results; product+offers+stats calls cost more per ASIN); the Creators API has its own rate limits tied to your Associates tier. `DEAL_DISCOVERY_LIMIT` already caps per-run volume — worth watching actual token consumption as you increase it.

**Operational visibility.** A pipeline that silently breaks is worse than one that loudly breaks. A Slack/Discord webhook (or n8n's built-in error workflow) firing on sync failures means you find out same-day, not when a customer emails asking why a deal is dead.

**Housekeeping.** A `--dry-run` flag on `syncDeals.js` so future changes can be tested without touching Supabase or burning a LinkTwin call.

## Bigger scope, explicitly deferred (not forgotten)

Two features came up while comparing against a reference site (damgooddeals.ca) and were deliberately pushed later rather than scoped now: **multi-retailer support** (pulling deals from Home Depot/Best Buy/etc. alongside Amazon — a second discovery+verification pipeline per retailer, real backend expansion) and **user accounts with synced saved/liked deals** (vs. the current localStorage-only bookmarks — needs Supabase auth + a user-scoped table), which the user wants to tackle once the core site is live. Also still open from that comparison: a site-wide affiliate disclosure footer (same Associates compliance category as the `last_verified_at` badge, just a static one-time addition) and wiring the frontend's category filter chips to the real `category` values Keepa returns instead of the current hardcoded placeholder list.

## What I'd suggest doing next

Compliance's backend half is done — run the `last_verified_at` migration above before the next scheduled sync (if not already done), then hand the frontend contract to whichever chat owns `DealCard.jsx` so the badge actually shows up. The EXPIRE sweep is now built too. Next up, in rough order: the affiliate disclosure footer (quick, same compliance category), then wiring real categories into the frontend filter — both small. After that, the glitch-pricing ceiling guardrail and operational alerting round out the "won't silently do something wrong" list.
